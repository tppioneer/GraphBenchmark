# 项目控制台策略（可选）

状态：可选策略，不属于通用 Skill 的默认行为。

## 启用方式

仅当用户明确要求“按 controller policy 执行”、在任务卡中引用本文件，或在当前对话中明确授权时，控制器才应用本策略。

本文件不修改或扩展 `.agents/skills/orchestrate-long-running-development` 的默认发布行为，也不适用于其他项目。

## 角色边界

Codex 作为控制台，只负责：

- 固定任务输入、设计来源、工作树、分支和完整基线 SHA；
- 验证执行器交付的 commit、改动范围、工作树状态、检查证据和状态机转换；
- 调度独立实现、复审和修复；
- 记录任务卡、审查记录、验证状态和集成记录；
- 在已授权的本地集成范围内，按通过的审查证据顺序合入提交。

Codex 不直接实现功能、修复缺陷、编写任务测试或自行执行独立代码审查；这些具体任务交由执行器完成。

## 执行器标准

- 执行器和复审器均使用 Claude Code CLI。
- 每次调用显式指定模型 `glm-5.2`。
- 使用非交互模式、自动权限模式，并限制工具集到任务所需的最小范围。
- 每个写入任务使用专用分支和隔离工作树；复审使用独立、只读工作树。
- 执行器必须使用仓库 `.venv` 运行任务卡规定的验证命令。
- 禁止真实 Judge 调用、凭据读取/写入、生产操作或未授权外部操作；除非任务卡和用户明确允许。

## 派发与交付

每次派发必须向执行器提供：

- 仓库和工作树的绝对路径；
- 任务卡路径、分支和完整 `Expected HEAD`；
- 允许范围、排除范围和引用的设计章节；
- 明确的验证命令；
- 严格的 `AGENT_RESULT` 或 `REVIEW_RESULT` 返回格式。

执行器必须先验证 `git rev-parse HEAD` 与 `Expected HEAD` 相同；不相同则不修改并返回 `BLOCKED`。任务卡和审查文档由控制器拥有，执行器不得修改。

## 自动闭环

对于任务卡、设计约束和验收标准已明确的工作，控制器自动推进：

`IMPLEMENTING → READY_FOR_REVIEW → CHANGES_REQUIRED（如需要） → VERIFIED → INTEGRATED`

- 执行交付后，控制器验证 base/head 祖先关系、提交存在性、范围、检查证据与工作树干净度。
- 所有实现均需由独立 Claude Code 复审；复审必须检查实际累计 diff，而非仅采信执行器报告。
- 已证实、无需求歧义的缺陷自动形成窄范围修复包，修复后重新复审。
- 通过最终复审的提交，在用户已授权本地自动集成时可自动按顺序合入目标分支。
- 不推送远端、不创建 Pull Request、不发布或执行生产操作，除非用户另行明确授权。

## 状态检查节奏

- 任务启动后，首次常规状态检查不早于约 10 分钟。
- 后续无异常时同样以不少于约 10 分钟的间隔检查，避免高频轮询和不必要的控制台消耗。
- 用户主动询问状态、执行器已返回、或出现明确失败信号时，可以立即检查。
- 如运行环境不支持控制器定时唤醒，不得声称会在后台自动检查；应在下一次可执行控制器轮次遵循该间隔。

## 必须暂停并请求决策的情形

- 设计、协议、数据模型、版本兼容或验收语义存在实质歧义；
- 修复会扩大任务允许范围，或需要改变已冻结的决策；
- 需要真实模型调用、成本支出策略、凭据处理、外部系统写入、发布或生产操作；
- 审查发现问题无法由现有任务卡和设计确定性解决。

此类情形必须附上证据、可选方案和建议，不得由控制器自行假设。
